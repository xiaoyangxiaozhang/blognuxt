这次问题的现场很简单：电脑上模型会转，鼠标也能拖；我拿手机打开，手指在模型上来回划，模型一点反应都没有。

页面没有报错，模型也不是白屏。它就安安静静地站在那里，像是在说：你可以看，但别碰我。

我一开始甚至怀疑是手机浏览器不支持，或者这个 glTF 文件在移动端加载失败。后来才发现，模型其实已经加载好了，真正被我关掉的是“让手指控制它”的那一层。

## 这个模型放在哪里

博客现在没有单独的 `about.vue`，关于和留言的内容放在 `/message` 页面里。页面左边是一些关于我的介绍，右边放了一个可以自转、也可以交互的 3D 模型。

模型组件是 `app/components/about/AboutModel.vue`。它没有在服务端直接创建 WebGL，而是通过 `<ClientOnly>`，等浏览器挂载以后，再在 `onMounted` 里创建 renderer、camera、scene 和 controls。

这样做不是为了把代码写得复杂，而是因为服务端没有 `window`、`document` 和 WebGL。SSR 阶段先展示“正在加载 3D 模型”，浏览器接手以后再真正创建画布，至少不会因为服务端执行 Three.js 而整页出问题。

## 第一个误判：是不是模型没有加载

遇到“不能旋转”时，我第一反应是检查模型文件。

模型文件通常不只是一个 `.gltf`。它旁边可能还有 `.bin` 和纹理目录，路径错一个，桌面端和移动端的表现可能还不一样。于是我先看加载回调、模型状态和网络请求，确认模型确实进入了 `ready` 状态。

这一步很重要，因为“模型没加载”和“模型加载了但不能交互”是两条完全不同的排查路线。

如果模型没加载，要去看路径、相对资源、CORS 和 loader；如果模型已经显示出来，再继续盯着资源文件，往往只是绕远路。

## 真正的原因藏在一个看起来很合理的判断里

原来的代码里有这样一段逻辑：

```ts
const coarsePointer = window.matchMedia('(pointer: coarse)').matches
controls.enabled = props.enableControls && !coarsePointer
```

它的出发点其实不坏。粗指针设备通常就是手机和平板，我当时大概是担心触摸手势和页面滚动打架，所以在这类设备上直接关闭 OrbitControls。

问题是，关闭之后确实不会打架了——因为只剩页面滚动，模型也彻底失去了旋转能力。

这类代码很容易让人误以为自己做了“移动端适配”。实际上，我只是把移动端功能关掉了。桌面浏览器上测试没有问题，不能说明触摸设备上的交互也成立。

最后我把开关改成只由组件配置决定：

```ts
controls.enabled = props.enableControls
controls.enablePan = false
controls.enableZoom = props.enableZoom
```

关于页面把 `modelControl` 作为配置传进来。需要能拖动的地方就打开，需要纯展示的地方就关闭。这个决定权不该由“设备是不是粗指针”一刀切掉。

## 打开控制以后，页面滚动怎么办

模型能拖动以后，新的问题马上出现了：如果手指在模型区域滑动，浏览器到底应该理解成“旋转模型”，还是“向下滚页面”？

我不希望为了让模型能转，就把整个区域变成一个只能玩模型、不能正常滚动的黑洞。博客首先还是一个阅读页面，移动端上下滑文章必须顺手。

最后保留了三个取舍：

- `enablePan = false`，不允许把模型拖离视野；
- 缩放单独由 `enableZoom` 控制，关于页默认不强行开启；
- canvas 使用 `touch-action: pan-y`，把页面纵向滚动保留下来。

这不是一个完美的手势设计，但它符合我更在意的顺序：能看、能滚、需要时能转。3D 模型是页面的一部分，不应该反过来支配整页。

## 第二个坑：模型的原点不在它看起来的中心

移动端的问题修好以后，我又遇到一个看起来像“旋转不自然”的问题。

模型可以旋转，但旋转中心有点奇怪。有时像是绕脚底转，有时像是围着模型旁边某个看不见的点转。看起来不是模型坏了，是模型文件自己的坐标原点不一定在几何中心。

所以加载完成后，我先用 `Box3` 取出模型的包围盒中心，再把这个中心平移到场景原点：

```ts
model.updateMatrixWorld(true)
const box = new THREE.Box3().setFromObject(model)
const center = new THREE.Vector3()
box.getCenter(center)
model.position.sub(center)
model.updateMatrixWorld(true)
```

相机也不能写死一个距离。不同模型的大小不一样，我用包围球半径估算相机距离，再让 OrbitControls 的 target 对准模型中心。这样以后换一个尺寸不同的模型，至少不用先手动猜一组位置。

## 我差点为了修旋转，把模型自带动画弄丢了

这个模型文件本身还带有动画。最初为了处理旋转中心，我把模型放进了一个额外的 `modelPivot`，然后让 pivot 自转。

这在数学上没有错，但场景里其实同时有两种运动：模型文件自己的骨骼动画，以及外层容器的整体旋转。如果只盯着“模型在转没转”，很容易把内置动画、场景旋转和用户拖动混成一件事。

后来我把这几层关系重新拆开：

```ts
if (gltf.animations.length) {
  mixer = new THREE.AnimationMixer(model)
  gltf.animations.forEach((clip) => mixer?.clipAction(clip).play())
}

clock.update()
const delta = clock.getDelta()
mixer?.update(delta)
scene.rotation.y += delta * 0.18
controls?.update()
```

模型自己的动画交给 `AnimationMixer`，整个场景的自转交给 `scene.rotation`，用户的拖动交给 OrbitControls。每一层只做自己的事情，后面再看行为就清楚多了。

还有一个小细节：`THREE.Timer` 要先 `update()`，再拿 `getDelta()`。时间顺序写反，动画可能不会按预期推进，或者在切换页面、切换标签后出现奇怪的跳动。

## 这次排查真正让我记住的几件事

第一，看到“移动端不能用”，不要马上把锅甩给移动端。先确认代码是不是主动把功能关闭了。很多所谓的兼容性问题，最后只是一个 `&& !coarsePointer`。

第二，模型显示出来，只能证明资源加载和渲染链路基本通了，不能证明交互通了。渲染、自动旋转、内置动画、触摸控制，应该分别验证。

第三，修复一个交互问题时，不要顺手删掉旁边看起来相关的行为。自动旋转、模型动画、相机跟随和用户拖动虽然都表现为“模型在动”，但它们的责任完全不同。

第四，电脑上的鼠标拖动不等于手机上的手指拖动。至少应该在真实触摸环境里验证一次，而且要同时测试“拖模型”和“滑页面”，不能只确认模型会转。

## 现在的结果

现在 `/message` 上的模型会在浏览器端加载，默认保持自己的动画和缓慢自转；开启控制后，移动端可以用手指旋转，页面的纵向滚动也还在。模型资源加载失败时，组件会显示备用内容，而不是让页面留下一个空白区域。

我不把这件事叫作“3D 交互完美解决了”。模型大小、浏览器手势、低端设备性能和不同 glTF 文件的原点，仍然可能带来新的问题。只是这一次，至少把几个原本纠缠在一起的开关和运动来源拆开了。

## 写在最后

我挺喜欢这个小模型，但我不希望它抢走页面的注意力。

它可以慢慢转，可以让访客拖两下看看，也可以在加载失败时安静地退到一边。博客里还有文章、留言和很多没整理完的想法，3D 只是其中一个小小的入口。

这次问题最后没有落到什么高深的移动端黑魔法上，只是我终于认真承认了一件事：

有时候不是手机不配合，是我先替手机做了决定。
