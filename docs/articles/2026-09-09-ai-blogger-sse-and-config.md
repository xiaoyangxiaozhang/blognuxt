我给博客加聊天功能，最开始并不是因为“现在的网站都应该有一个 AI”。

我只是觉得，博客如果只有文章列表、分类、标签和几个按钮，多少有一点安静过头了。访客看完文章就走了，想问一句“你最近在折腾什么”，也只能去找评论区。可评论区更像是留下来的话，不太像当场聊两句。

所以我想试试，在博客里留一个可以说话的“我”。不一定每次都回答得多厉害，也不一定能替我解决所有问题，但至少有人问的时候，它可以先接住这句话。

当然，这句话听起来很浪漫，真正写起来还是一堆接口、状态和边界。

## 我不想让访客等到最后才看到一整段话

最直观的实现，是前端发一个请求，后端等模型完整回答后，再把整段文本返回来。这个方案当然能跑，但体验有点像把信塞进门缝里：访客要等里面的人写完，外面才知道到底有没有回应。

我更希望它像聊天。先出来几个字，接着一句一句往下长，哪怕回答稍微慢一点，页面也不是完全没有动静。

最后我选了 SSE。它不负责解决所有问题，但很适合现在这个场景：请求还是一个普通的 HTTP 请求，服务端可以持续往前端推送事件，浏览器不用一直轮询“你回答完了吗”。

现在这条链路大概是这样：

```text
访客输入一句话
    -> Nuxt ChatbotWidget
    -> POST /api/v1/chatbot/chat/stream
    -> Go ChatbotController
    -> ChatbotService
    -> OpenAI 兼容接口
    -> SSE 推回 ready / delta / done
```

这里的 `chatbot` 是独立的一组配置。以后接什么兼容接口、使用哪个模型，应该是后台配置问题，不应该逼着前端再改一次代码。

## SSE 对我来说不是为了显得高级

SSE 的事件很简单，我没有设计一套特别复杂的协议。开始时发一个 `ready`，模型有新内容时发 `delta`，结束时发 `done`，出错时发 `error`。

大概长这样：

```text
event: ready
data: {}

event: delta
data: {"content":"我最近在整理"}

event: delta
data: {"content":"博客的文章和交互。"}

event: done
data: {"sources":[]}
```

前端没有用 `$fetch` 来处理这条流，而是在 `app/services/api/chatbot.ts` 里直接使用原生 `fetch`，再通过 `response.body.getReader()` 一段一段读取。

这是因为普通的 `$fetch` 更适合“请求发出去，最后拿到一个 JSON”。流式响应还没结束时，它不会把中间结果交给页面。对普通接口来说这很正常，但对聊天来说，就会变成按钮点下去以后长时间沉默。

读取过程里还要自己处理几个小问题：网络分块不一定刚好落在事件边界上，换行可能是 `\\r\\n`，一条事件也可能被拆成几次才收完整。所以前端需要留一个 buffer，等看到两个换行，再把这一段当作完整事件解析。

这类代码看着不长，但我觉得它很能说明一件事：用户感受到的“流式”，并不只是把接口名字改成 stream。前后端都要认同同一种事件边界，连接中断时也要给用户一个能看懂的结果。

## 我把聊天配置和其他 AI 功能分开了

博客原来已经有一些 AI 相关配置，比如摘要和标题生成。聊天机器人虽然也调用模型，但它和文章总结不是一回事。

文章总结追求的是稳定、简洁和批处理；聊天机器人更在意语气、历史消息、对话边界和访客体验。如果共用一套 API Key、模型和提示词，短期看少几个字段，长期很容易互相牵制。

所以后台单独增加了“聊天机器人”配置组，里面可以设置：

- 是否开启公开聊天；
- 显示名称、头像和欢迎语；
- Base URL、API Key、模型和温度；
- 说话风格、常用表达和避免表达；
- 对话边界、示例对话和历史消息数量；
- 频率限制和每日调用上限。

API Key 只留在后端。前台请求公开配置时，只拿到聊天窗口真正需要的内容，不会把密钥塞进 Nuxt 的公开配置，也不会让浏览器知道模型供应商的后台设置。

这件事没有什么特别花哨的技巧，主要是别嫌麻烦。能放在服务端的秘密，就不要因为“反正现在只有我自己用”而放到前端。

## 人格不是把欢迎语改得可爱一点

如果只把聊天窗口放上去，再给它一句“你好，我是博主”，它很快就会变成一个普通问答框。访客问它“你是谁”，它讲一遍身份；再问一次，它再讲一遍。语气看起来礼貌，但没有什么“人”在里面。

我想要的不是一个客服，而是博客主人本人在这里留了一点说话的痕迹。

所以系统提示里约束了几件比较具体的事：

第一，尽量用我的第一人称说话。博客里的技术经历、建站故事、性格、座右铭和文章内容，都可以作为它了解我的公开资料。

第二，普通聊天短一点，像朋友之间接话，不要每次都写成一篇小论文。该吐槽的时候可以吐槽，有不确定的地方也不要硬装知道。

第三，资料里没写过的现实经历不编。它可以自然地说：“这个我没在博客里写过，不瞎说。”这比一本正经地编一个完整故事可靠得多。

我挺喜欢“前景可待，未来可期”这句话，但我也不想让它每次回答都把座右铭挂在嘴边。人格应该是回答时的底色，不是固定贴纸。

## 文章推荐不能顺手乱发链接

聊天功能接入文章知识后，还有一个容易忽略的细节：访客只是普通闲聊时，不应该每次都被塞一篇文章链接。

现在只有访客明确表达“推荐一篇文章”“有没有相关内容”这类意图时，后端才会从已发布文章里取真实文章，返回固定的标题和地址。模型负责写一两句推荐理由，不能自己编文章名，也不能自己拼一个看起来像真的链接。

这个边界看起来有点细，但它直接影响信任感。博客里不存在的文章，哪怕标题起得再像，也还是不存在。链接错一次，访客以后看到“顺手看看”可能就不敢点了。

## 我现在能确认什么，不能确认什么

目前本地代码已经把前台聊天窗口、普通 JSON 接口、SSE 流式接口、后台独立配置和文章推荐边界串起来了。构建和路由层面的检查也做过。

但我不想把“接口能返回 400”写成“模型已经在线聊天成功”。没有填入真实可用的模型密钥，就不能证明外部模型调用一定成功；没有在生产环境完整走一遍，也不能把本地结果说成线上结果。

这也是我写这篇记录的原因之一。做个人项目很容易为了让文章看起来完整，把“已经写了”“本地跑过”“线上验证过”混成一句话。可它们本来就是三件不同的事。

## 写在最后

我现在还不确定这个 AI 博主最后会变成什么样。

也许以后它会更懂文章内容，也许会因为回答太像说明书而继续被我改；也许访客真的会和它聊起来，也许最后大家还是更喜欢直接给我留言。这些都没关系，先让它待在博客里，看看它能不能慢慢长出一点自己的语气。

我更在意的不是“博客拥有了 AI”这件事，而是访客打开页面时，除了看文章，还能有一个入口问一句：

“你最近在忙什么？”

然后这里真的有人接话。
